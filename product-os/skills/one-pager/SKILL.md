# One-Pager Generator

Produce the document that earns an idea its first meeting: one page, problem-first, honest about uncertainty.

## Before writing anything

1. Read `foundations/business-strategy.md` — which pillar/priority does this ladder to? If none, the one-pager must make an explicit "why anyway" case.
2. Read `foundations/wealth-lobs.md` — name the LOB(s) whose problem this is.
3. Check `foundations/practice-frameworks.md` for a house one-pager template; if present it overrides the default structure below. Also check `foundations/product-design-practice.md` "Definitions of quality" for what a good one-pager must contain.

## Default structure (strictly one page)

1. **Problem** — who hurts, how much, and how we know. Client language, not internal language. If evidence is thin, say "hypothesis" plainly.
2. **Why now** — the strategic hook (cite the pillar/priority) plus any timing forcing-function.
3. **Opportunity size** — order-of-magnitude only, with the arithmetic shown.
4. **Proposed direction** — 2–3 sentences maximum. This is a direction, not a spec; resist detail.
5. **Smallest real test** — the cheapest thing that would generate evidence, and what result would kill the idea.
6. **Who's affected** — LOBs, shared platforms, and any friction point from `wealth-lobs.md` this touches.
7. **Ask** — exactly what decision or resource is being requested.

## Rules

- One page means one page. Cut the weakest sentence until it fits.
- Problem before solution — if the user leads with a solution, extract the underlying problem and confirm it with them first.
- Flag anti-patterns from `product-design-practice.md` if the user's framing exhibits one (e.g. solution-first) — kindly, in a note above the draft, not inside the document.
- Where a needed foundation section is an unfilled `<!-- FILL -->` placeholder, note the gap in the draft rather than inventing content.
- Suggest the next stage-gate from the idea-to-delivery path when handing over the draft.
